# TaskNavi 初学者向け教科書

勉強を始める人は、先に **「12. 最初の2週間」** だけを上からやる。  
1〜11章と [study-checklist.md](./study-checklist.md) は辞書です。最初から最後まで読まない。

## 1. このプロジェクトで最初に押さえること
- 画面は Swing で作っています。Java に最初から入っている画面の部品です
- 部品の並べ方は、ほとんど MigLayout で決めています
- 画面ごとに、受け持つ仕事が分かれています
- 画面はデータを `TaskService` に頼みます。データベースを触るのは `Dao` だけです
- ある画面で変えたことは、`TaskEventBus` が他の画面に知らせます

## 2. 全体構成の考え方

フォルダは役割で分かれています。いちばん上には、起動の `Main`、エラーの `AppException`、文言の `AppMessages`、アプリの版の `AppVersion` だけを置きます。

- `model` はデータの形（`Task` など）
- `service` は保存の仕事（`TaskService`、期限の判定の `DueTasks`）
- `persistence` は自分だけのタスクのデータベース（`Database`、`TaskDao`）
- `team` は共有プロジェクトの記録の読み書き（入口は `TeamProject`。16章）
- `io` は CSV と JSON の読み書き（`TaskCsv`、`TaskJson`）
- `util` は絞り込みと状態の小さな計算（`TaskViewFilter`、`TaskStatusCycle`）
- `event` は画面への知らせ（`TaskEventBus`）
- `ui` は画面。直下には、どの画面でも使う部品（`AppTheme`、`AppDialog`、`DatePickerDialog` など）を置きます。中は次のフォルダに分かれます
  - `ui/main`: メインの窓（`MainFrame`）と、ヘッダー・検索欄などその部品
  - `ui/today`・`ui/wbs`・`ui/kanban`・`ui/gantt`・`ui/calendar`: 5つのタブ
  - `ui/taskdialog`: タスクを作る・直す窓
  - `ui/team`: 共有プロジェクトの画面（「プロジェクト ▼」の `ProjectSwitcher` など）

## 3. よく出てくる名前
- `JFrame` はウィンドウ、`JDialog` は小さな窓、`JPanel` は部品を入れる箱
- `MigLayout` は部品の並べ方
- `ActionListener` はボタンを押したときの処理
- `LocalDate` は日付
- `TaskService` は保存の窓口、`TaskDao` はデータベース
- `persistence` の中の `TaskRowMapper` / `TaskHierarchySupport` / `TaskCrudDao` / `TaskImportDao` は、データベースの読み書きを分担しています
- `TaskEventBus` は他の画面への知らせ
- `AppTheme` は色、`AppMessages` は画面の文言
- `IconManager` はアイコン
- `SearchablePanel` は、上の検索欄で絞り込める画面の印

## 4. MigLayout の見方
- `fill`: 使える場所いっぱいに広げる
- `insets`: 外側の余白
- `gap`: 部品と部品のすき間
- `wrap`: そこで次の行に行く
- `grow`: 余った場所に合わせて伸びる
- `align right/left/center`: 右・左・真ん中に寄せる

## 5. 画面ごとの重要ポイント
### ログインはありません
- 起動すると、スプラッシュのあとすぐメイン画面が開きます。アプリのアカウントやパスワードはありません
- 自分だけのタスクは、その PC のデータベースにあります。守りは Windows のログインに任せます（1人1台の PC で使う前提）。アプリにパスワードを付けても、データベースのファイルは直接開けるので、守りにならないためです
- 共有プロジェクトでの「自分」は、表示名（`TeamSettings.displayName`）と PC ごとの端末 ID で決まります。表示名は「プロジェクト ▼」のメニューで決め・変えます
- 前の版（1.1.0 まで）のログイン用のアカウントとタスクの持ち主は、データベースの更新 `V6__drop_login.sql` で外しました。どのアカウントのタスクも消さず、全部「この PC のタスク」になります

#### ログイン画面を消した理由（1.2.0）
1.1.0 までは、起動するとログイン画面が出て、登録・ログイン・メールでのパスワード再設定がありました。1.2.0 で全部消しました。理由は次の5つです。

1. **守りになっていなかった。** タスクは PC の中の `tasknavi.db` にあり、暗号化していません。アプリにパスワードを付けても、ファイルを直接開けば中身は読めます。本当の守りは Windows のログインで、アプリのログインは同じことを二重にしていただけでした
2. **パスワードを忘れたときの対応が重かった。** 再設定にはメールを送る仕組みが要り、各 PC にメールの送信設定（SMTP のサーバーとパスワード）を入れる必要がありました。サーバーを置かない小さなチームでは、それを用意して保つ人がいません。設定が無いと、忘れた人は自分のタスクを開けなくなります
3. **共有プロジェクトの本人確認には使えなかった。** 共有は Google ドライブのフォルダで、サーバーがありません。アカウントは各 PC の中にしか無いので、他の PC からはそれが本人かどうか確かめられません。共有では、もともと表示名と PC ごとの端末 ID で「誰が書いたか」を記録していて、フォルダを見られる人は Google ドライブの共有設定で決まります
4. **1人1台の PC では分ける意味が薄かった。** アカウントごとにタスクが分かれるため、同じ PC で別のアカウントを作るとタスクが見えなくなったり、サンプルが2組入ったりして、かえって迷う元になりました
5. **作りが小さくなる。** ログイン画面、パスワードの保存（bcrypt）、メール送信（jakarta.mail）、試行回数の制限、再設定コードの表など、使い道の薄い部品をまとめて外せました。直す場所と、壊れる場所が減ります

代わりの考え方:
- 自分だけのタスクの守りは Windows のログインに任せます。1台の PC を何人かで使うときは、Windows のユーザーを人ごとに分けます。データの場所（`%APPDATA%\TaskNavi`）は Windows のユーザーごとに別なので、タスクも自然に分かれます
- 共有プロジェクトで誰が見られるかは、Google ドライブのフォルダの共有で決めます
- もしサーバーを置いて、社外から使うなどの形に変えるときは、そのときにサーバー側で本人確認を作り直します。PC の中だけのログインに戻しても、上の 1 と 3 は解決しません

### MainFrame
- アプリ全体の土台です
- いちばん上の帯（ヘッダー）に、プロジェクトの切り替え・共有で使う表示名・インポート／エクスポート・テーマがあります。表示名をまだ決めていなければ、名前は出ません。その下の帯（ツールバー）に、検索と絞り込みがあります
- 真ん中はタブです: 今日 / WBS / カンバン / ガント / カレンダー
- 起動すると、いつも「今日」のタブから始まります。前回のタブは覚えません（毎朝まず今日のタスクを見るため）
- 上の検索欄の文字は、各タブの `SearchablePanel` に渡ります
- 今かかっている絞り込みの説明文は、`MainGlobalSearchBar.describeFilters` が作ります
- エクスポート／インポートは `TaskDataIoHelper` です。形式は CSV（Excel で編集する用）と JSON（TaskNavi 同士で移す用）
  - エクスポートでは、全件か、絞り込んだ分だけかを選べます。絞り込んだときも親（プロジェクト・工程）は一緒に書き出します。親がないと取り込み直したときに階層が組めないためです
  - CSV の読み書きは `io/TaskCsv`、区切り・引用符・文字コードの細かい処理は `io/CsvCodec` です。書き出しは BOM 付き UTF-8（Excel で文字化けしない）、読み込みは UTF-8 と Shift_JIS（Excel の普通の保存）の両方を受け付けます
  - 日付は `2026-10-24` / `2026/10/24` / `2026年10月24日` のどれでも読めます。状態・優先度は「進行中」「高」のような日本語で書きます
  - 親子関係は「ID」「親ID」列で表します。取り込むときは ID を振り直し、親を先に保存してから子の親 ID を新しい ID に付け替えます（`TaskImportDao`）
  - 読めない行があっても、ほかの行は取り込めます。取り込む前に件数と「何行目がなぜ駄目か」を出し、「今のタスクに追加」か「すべて置き換え」を選びます。置き換えのときは、消す前のタスクを `backups` フォルダに `before-import-日時.csv` として残します
  - `=` `+` `-` `@` で始まる値は Excel が数式として実行してしまうので、書き出し時に先頭へ `'` を付け、取り込み時に外します
- MainFrame が長くならないよう、部品ごとに別のファイルにしています
  - ヘッダー: `MainHeaderBar`
  - 検索欄: `MainGlobalSearchBar`
  - テーマの切り替え: `MainThemeSupport`
  - ツールバーのボタン: `MainToolbarButtons`
  - 追加の流れ: `MainTaskAddHelper`
  - タブの見た目: `MainTabChrome`

### TodayPanel（`ui/today`）と期限の通知
- 期限切れ・今日まで・7日以内の、終わっていないタスクを並べます。子を持つタスクは出しません
- 自分だけのタスクと、最近開いた共有プロジェクトのタスクを、まとめて出します。プロジェクトが2つ以上あると、名前の横にどのプロジェクトかの札が付きます（くわしくは16章）
- どれをどこに入れるかは `service/DueTasks` が決めます。画面と通知で同じものを使います
- 共有プロジェクトを使っていると、右上に「自分の担当だけ」が出ます。初めはオンで、共有プロジェクトのタスクは、担当者が自分の表示名か空のものだけを出します。自分だけのタスクは全部出します。期限の通知も同じ設定で数えます（`TodayPanel.onlyMine`、`TaskSource.isMine`）
- 「完了」ボタンは `TaskStatusChanger`、ダブルクリックの編集は `TaskEditHelper` を通ります。どちらも、そのタスクのプロジェクトの `TaskService` に書きます
- `DueReminder` が、起動したときと日付が変わったときに、Windows の通知で件数を知らせます。件数も全部のプロジェクトの合計です。日付が変わったら全画面を描き直させます。共有プロジェクトで他の人が自分の担当を変えたときの通知も、同じ `DueReminder` の通知アイコンから出します（`showNotices`。くわしくは 16 章）

### WbsPanel / KanbanPanel / GanttPanel / CalendarPanel
- 仕事の中心になる4つの画面です。どれも `TaskService` を受け取ります
- 置き場所は `ui/wbs`、`ui/kanban`、`ui/gantt`、`ui/calendar` です
- 見るところは、タスクの一覧、状態、操作ボタンのつながりです
- 画面の描き直しは、`refresh` で始まるメソッドと `TaskEventListener` を見ます
- 期限切れは `Task.isOverdue()` です。終わっていなくて、終了日が今日より前なら期限切れです。カレンダーとカンバンのカードで目立たせます
- どの画面も、1つのファイルに全部は書いていません。同じフォルダの中で分けています
  - WBS: ツリーの組み立て、絞り込み、ドラッグでの並べ替え、右側の詳細、登録
  - カンバン: 絞り込み、カード、列への振り分け。上の「担当者」で1人に絞れて、「担当者ごとに分ける」をオンにすると各列の中が担当者の見出しで分かれます（`KanbanAssignees`。オン・オフは PC ごとに覚えます）。分けても、列の間のドラッグで状態を変えるのは同じです
  - カレンダー: 月や週の切り替え、月表示と週表示、日ごとの横の一覧、カード
  - ガント: 線の描画、クリックした場所の判定、ドラッグ、横の列
- 状態を1つ前・1つ後ろへ動かすのは `util/TaskStatusCycle` です

### TaskDialog
- タスクを作るときと直すときの窓です（`ui/taskdialog/TaskDialog`）
- 種類は `EntryType` で、プロジェクト・フェーズ・タスクの3つです
- 日付の欄は `DatePickerDialog` と一緒に動きます
- 新しく作るタスクの中身は `TaskEntryFactory` も見ます
- 親の選択肢、入力欄、保存前のチェックは、同じフォルダの別ファイルにしています
- 一番下にメモ欄があり、改行して何行でも書けます。メモ欄の中では `Tab` で次の欄へ移り、`Ctrl+Enter` で保存します
- メモはデータベースの `memo` 列に入ります（`V5__task_memo.sql`）。WBS の右側の詳細と、今日タブの行にマウスを乗せたときにも出ます

### キーボード操作（`MainFrame.installShortcuts`）
- `Ctrl+F`: 検索欄へ移る
- `Ctrl+N`: タスクを追加する
- `Enter`: 選んでいるタスクを編集する（`TaskEditHelper` で開きます）
- `Delete`: 選んでいるタスクを消す
- 文字を入力している途中は、`Enter` と `Delete` は効きません

### DatePickerDialog（`ui/DatePickerDialog`）
- 日付を選ぶ小さな窓です。いろいろな画面で使い回します
- 見るところは、`LocalDate` で月を進めたり戻したりするところと、日付のボタンを作るところです

### 検索（`ui/main/MainGlobalSearchBar`）
- 上の検索欄に1文字入れるたびに、今の画面を絞り込みます
- タスク名だけでなく、担当者の名前やメモの中身、共有プロジェクトならコメントの中身でも見つかります（`TaskViewFilter.matchesKeyword`。削除したコメントは見ません）。WBS も同じ判定を使います
- 各画面は `SearchablePanel` の `applySearchFilter` を持っています

## 6. よく見る書き方
- `getSelectedItem()` で、コンボボックスで選ばれている項目を取る
- `setText` で入力欄に文字を入れ、`getText` で取り出す
- `addActionListener` で、ボタンを押したときの処理を登録する
- `setVisible(true)` で窓を出す
- `dispose()` で窓を閉じる
- `LocalDate.parse()` で文字を日付に変える。変えられなければ、日付の書き方がおかしい
- 状態などの画面の文字は `AppMessages` から取ります。データベースには `NOT_STARTED` のような英語のコードで保存します

## 7. まちがえやすいところ
- `null` かどうかを確かめずに使うと、アプリが落ちます
- `JComboBox` の中の値（コード）と、画面に出す文字がずれると、おかしな動きになります
- `wrap` を忘れると、部品が横にずっと並びます
- ダークモードでは、背景の色と文字の色の両方を確かめます。複数行の入力欄は `AppTheme.createStyledTextAreaScroll` で作ると、他の入力欄と同じ色になります
- 画面のファイルに `new Color(...)` を直接書きません。ライトとダークで変わる色は `AppTheme.cardBackground()`・`textStrong()`・`danger()`・`progressTrack()` などのメソッドから取ります。色を `static final` の定数に入れると、テーマを切り替えても古い色のまま残ります（カンバンの進捗バーの溝がダークモードで白く光っていたのはこれです）。白い文字を載せる札の塗りだけは、どちらのテーマでも同じ `AppTheme.FILL_*` です。状態の文字（未着手・完了など）は `AppTheme.statusText(...)`、ガントの地の色は `ganttStripe()`・`ganttWeekend()` などから取ります
- スクロールバー・分割の仕切り・スクロール欄の枠は、Metal のままだとダークモードで白く浮きます。`ModernScrollBarUI`・`ModernSplitPaneUI`・`AppTheme.ThemeLineBorder` が描くたびにテーマの色を取るので、画面ごとに直す必要はありません。テーマ切り替えで色が戻らない部品は、`MainThemeSupport.applyToContainer` に1行足します
- 白い文字を載せる青のボタンは `AppTheme.primaryFill()` で塗ります。ダークの `PRIMARY` は線や文字用の明るい青なので、白い文字を載せると読めません
- `ThemeContrastTest` が本物のメイン画面を両方のテーマで開き、切り替えたあとも含めて全タブの文字と背景の差（コントラスト比 3 以上）を確かめます。選択欄の開いた一覧の行（カーソルを合わせた行も）と、タスクの編集画面も見ます。画面を直してこのテストが落ちたら、名前の出た部品の色をテーマから取るように直します
- 縦にスクロールする一覧や詳細は、`WidthTrackingPanel` の上に置きます。置かないと、長い名前で横にはみ出し、右端のボタンが切れます。縮めてよい文字には MigLayout で `wmin 0` を付けます
- 窓は 960×560 より小さくできません（`UiConstants.WINDOW_MIN_WIDTH_MAIN`）。画面を直したら、この大きさでも切れないか確かめます
- 画面から `TaskDao` を呼ばない。必ず `TaskService` を通します
- 本番の `TaskService` は `TaskService.createDefault()` で作ります。画面が `new TaskDao()` することはありません
- GitHub Actions（`.github/workflows/ci.yml`）で `mvn verify` が動きます。テストのあと、テストが通った行の割合（JaCoCo）を確かめ、全体で 60%、共有の記録の読み書き（`team`）で 90%、共有の画面（`ui/team`）で 25% を下回ると止まります。割合の表は実行結果の Summary に出て、詳しい HTML は `coverage-report` として14日残ります。自分のパソコンでも `mvn verify` で同じことを確かめ、`target/site/jacoco/index.html` をブラウザで開くと、どの行が通っていないかが色で分かります。1つのテストだけ動かすときは `mvn test` で、割合は確かめません
- 画面の土台を壊していないかは `MainFrameSmokeTest` で確かめます。タブの切り替え、検索欄を空にすること、テーマの切り替えを試しています

## 9. 設計の決まり
- 画面は、見せることと入力を受けることだけにします
- 「追加する」「消す」などの仕事は `TaskService`、データベースへの読み書きは `Dao` に置きます
- 何度も使う処理は1か所にまとめます（`TaskBusinessRules` / `SearchFilterUtil` / `TaskViewFilter` など）
- 色は `AppTheme`、文言は `AppMessages` から取ります
- 確認や選択の窓は `AppDialog` を使います。タスク編集の窓と同じ見た目になります
- フォルダの分け方は2章のとおりです。画面のフォルダは、WBS やガントごとにさらに分かれます
- 使わなくなったクラスやメソッドは、残さずに消します。残すと、どれが本物の処理か読む人が迷うためです（検索は `TaskViewFilter` だけ、入力チェックは `TaskWriteValidator` と `TeamTaskRules` だけ）
- 1つのクラスが大きくなったら、役割ごとに分けます。たとえば共有プロジェクトの入口の `TeamProject` は、`project.json` の読み書き（`TeamProjectFile`）・`members` フォルダ（`TeamMembers`）・書く前の確かめ（`TeamTaskRules`）・取り込み（`TeamImport`）を外に出し、記録を持って書き足すことだけをします。画面側の `TeamSession` も、裏側の列（`TeamBackground`）・開いていないプロジェクト（`TeamOtherProjects`）・5秒ごとの確認（`TeamPoll`）・更新の案内（`TeamUpdateHelp`）に分けています。外から呼ぶメソッドは変えないので、呼ぶ側とテストは直さずに済みます

## 10. 辞書の使い方

分からないクラス名が出たら、[study-checklist.md](./study-checklist.md) でその操作（操作A、操作D など）を探す。  
必読と書いてあるファイルだけ開く。関連は、必読が分かってからでよい。

## 11. データが守られている約束

画面は、データベースへ直接書きません。必ず `TaskService` を通ります。

- 保存に成功したときだけ、他の画面へ「変わったよ」と知らせます（`TaskEventBus`）
- 入力が不正なら、1件も書きません。画面には理由が出ます
- 編集の保存は `updateTask` です。中で `updateTasks` を1回呼び、成功したあとだけ他の画面へ知らせます
- 削除は、子タスクも含めて1回で消します。途中で失敗したら、全部元に戻します
- 消したあと10秒間、画面下の帯に「元に戻す」が出ます。押すと、子タスクも含めて元の ID のまま戻ります（`TaskService.restoreDeleted`）。その間に親が消されていたら、戻しません
- 並べ替えも1回で保存します
- 自分だけのタスクは、その PC の Windows ユーザーのものです。データベースには持ち主の欄がありません
- データベースを初めて作った起動のときだけ、サンプルのプロジェクトを入れます（`SampleDataUtil.insertSampleTasksIfEmpty`。初めてかどうかは `Database.takeCreatedNow` が、Flyway がまだ何も当てていなかったかで決めます）。前は「タスクが 1 件もなければ」入れていたので、本番を始めるときに見本を全部消すと、次の起動で見本が戻っていました。名前に番号は付けません（番号はツリーが付ける）。前の版で入った「1. 企画・要件定義フェーズ」などの番号は、データベースの更新 `V7__unnumber_sample_stages.sql` が外します
- データベースは `%APPDATA%\TaskNavi\tasknavi.db` に置きます。どのフォルダから起動しても同じです（`AppDataLocation`）
- 起動するたびに、その日の分がまだなければ `backups` フォルダにコピーを取ります。7日分残します（`DatabaseBackup`）。戻すときは、アプリを閉じてから、そのコピーを `tasknavi.db` という名前で上書きします
- ログは `%APPDATA%\TaskNavi\logs` に残します。今日の分は `tasknavi.log`、前の日の分は日付付きのファイルで、14日分だけ残します（`logback.xml` と `LogDirectoryDefiner`）。困ったことが起きたら、まずここを見ます。テストのときはファイルに書きません（`src/test/resources/logback-test.xml`）
- 読み込んだ全件は、次の書き込みまで `TaskService` が使い回します。書き込みは必ず `TaskService` を通るので、古いままにはなりません。ツールバーの更新ボタンで読み直せます

失敗の文面は `AppException` が持ちます。裏側の処理（`SwingWorker`）が包んでも、`ErrorDialogUtil.findAppException` が取り出して画面に出します。

### 例外の受け方

配った後に「何が起きたか」をログで追えるように、次の決まりで受けます。

- **操作の入口では何でも受けて、必ずログに残す。** 保存や削除の結果を受け取る所（`SwingWorker.done`）や共有フォルダの読み書き（`TeamBackground.run`）は、どんな失敗でも画面に出して止めずに続けます。画面に出すのは `ErrorDialogUtil.showBackgroundError` で、ここがログも書きます。入力の誤りなどの `AppException` は info に、想定外の失敗はスタックトレースごと error に残します。呼ぶ側では書きません（2回書かないため）
- **起こりうる失敗が決まっている所では、その種類だけ受ける。** 日付の読み取りは `DateTimeParseException`、フォルダ名は `InvalidPathException`、テーマの保存は `SecurityException | IllegalStateException`、ドラッグしたタスクの ID は `TaskDragData.taskId` が読み取りの失敗だけを受けます。前はカンバンのドロップで状態の変更まで `catch (Exception)` で囲んでいて、変更に失敗しても何も出ず、ログにも残りませんでした
- **どこでも受けなかった例外は `Main.handleUncaught` が受ける。** 必ずログに残します。起動の途中なら続けられないので知らせて終わり、メイン画面が出た後はお知らせ帯で知らせて使い続けられるようにします（保存は操作ごとに済んでいるため）。描画の中の失敗は続けて起きるので、お知らせは 30 秒に 1 回までです
- **5 秒ごとの確認の失敗は、変わり目だけ残す。** 共有フォルダを読めなくなったときに warn、また読めたときに info を 1 回ずつ書きます（`TeamSession.logPollResult`）。毎回書くとログがそれで埋まるためです
- **データベースの列は Flyway でそろっているので、列が無い場合に備えた `catch` は置かない。** 置くと、本当の SQL の失敗まで隠れます（`TaskRowMapper`）

1. TaskNavi は、自分のパソコンで動くタスク管理です。WBS、カンバン、ガント、カレンダーで、同じタスクを見ます。毎朝は「今日」のタブで、期限切れと今日までのタスクを見ます。チームのプロジェクトは、サーバーを置かずに Google ドライブの共有フォルダで共有します（16章）

### 聞かれやすい質問

1文で答えて、続きを聞かれたら話す。

- **なぜ Swing ですか**: Java に最初から入っていて、他に何も入れずに画面を作れるからです。1台のパソコンで動くアプリなので、Web にする必要がありませんでした。保存中に画面が固まらないよう、裏側で動かす（`SwingWorker`）ことも入れています
- **なぜ SQLite ですか**: データベースが1つのファイルで済み、サーバーを立てなくてよいからです。表の形を変えるときは Flyway を使い、`V1` から `V7` まで順番に当てています
- **どうやって配っていますか**: `jpackage` で、必要な分だけの Java を入れた `TaskNavi.exe` のフォルダを作り、zip にしています。使う人は Java を入れなくてよく、データは `%APPDATA%\TaskNavi` に置くので、アプリを入れ替えても消えません
- **Java の版はなぜ 25 ですか**: exe に Java ごと入れて配るので、入れた Java の修正が止まると、アプリごと古くなります。配る前に、修正が長く出る LTS の最新（25）に上げました。部品の更新は Dependabot が毎週知らせ、CI が通るものだけを取り込みます
- **管理者と一般で使えるボタンを分けないのはなぜですか**: チームで人を分けるのは Google ドライブの共有で行い、アプリでボタンを隠しても記録ファイルは直接書き換えられるからです。前の版にあった役割（`UserRole`）は、ログインと一緒に消しました。理由は15章の「やらないと決めたこと」に書いています
- **同時に編集したらどうなりますか**: 止めずに両方書きます。決まった順に並べて後ろの方を使い、消えた方の値は「重なった変更」として残すので、画面で見比べて戻せます。共有ドライブではロックが効くとは限らないので、ロックではなく「見つけて残す」にしました（16章）
- **記録が増え続けたらどうしますか**: 1回の変更は約 300 バイトで、5人が1日50回変えても年に約 20 MB です。5秒ごとに見るのはファイルの大きさと時刻だけで、変わったときだけ読み直します。遅くなったら、ある時点の一覧を1つのファイルにまとめ、それより前を読まない形にする予定です（README の「分かっている限界と、直す予定」）
- **なぜサーバーを使わずドライブにしたのですか**: 社内にサーバーも、ずっと動かしておく PC も置けなかったからです。チームはもう Google ドライブを使っていたので、共有の設定もそのまま使えます

## 15. 今はやっていないこと

ここは未完成ではなく、今の版の範囲です。面接では「次にやること」として話します。

- タスクが何万件になっても軽い読み方にすること。今は変更のたびに全件を1回読み直し、5つの画面で使い回します。件数が少ないうちはこれで足ります

### やらないと決めたこと: 管理者と一般で使えるボタンを分ける

前の版には、ログインする人ごとの役割（管理者と一般の `UserRole`）がありましたが、使わないまま、1.2.0 でログインと一緒に消しました（`V6__drop_login.sql` が `users` の表を外します）。社内の少人数のチームで使う前提では、要らないと判断しました。

- 共有プロジェクトに入れる人は、Google ドライブでフォルダを共有した人だけです。人を分けるのはドライブの共有で行います。見るだけの人は「閲覧者」で共有します
- アプリでボタンを隠しても、編集できる人はエクスプローラーから記録ファイルを直接書き換えられます。アプリの中の制限は、守りになりません
- 前の版の役割は PC ごとのデータベースにあり、共有プロジェクトのメンバーとはつながっていませんでした。チームの権限にするなら、共有の記録の側に作り直す必要があります
- まちがいを戻す仕組みはあります。変更履歴で誰が何を変えたか分かり、重なった変更と削除したタスクは戻せます。記録は足していくだけなので、前の変更は消えません

社外の人を入れるなど、メンバーを信頼できる前提が崩れたら考え直します。そのときは、共有フォルダではなくサーバーを置く形が必要です。

## 16. チームで使う（`team` フォルダ）

サーバーを置かずに、Google ドライブの共有フォルダ（Google Drive for desktop）を通して数人で同じタスクを見る仕組みです。画面左上の「プロジェクト ▼」で共有プロジェクトを選ぶと、今日・WBS・カンバン・ガント・カレンダーのどのタブにも、そのプロジェクトのタスクが出ます。「自分だけのタスク」を選ぶと、いつもの個人のタスクに戻ります。

共有プロジェクトを開いているあいだ、ボタンの右に「メンバー ○人」「同期中」が出ます。互いに知らずに変更が重なると、オレンジの「重なった変更 ○件」が出ます。メンバー・重なった変更・変更履歴・表示名の変更は、どれも「プロジェクト ▼」のメニューからも開けます。

### 全タブで共有プロジェクトを見る仕組み

```
各タブ → TaskService → TaskStore ─┬─ TaskDao        （自分だけのタスク。SQLite）
                                  └─ TeamTaskStore  （共有プロジェクト。TeamProject）
```

- タブはどれも `TaskService` からしか読み書きしません。`TaskService.useStore` で保存先を差し替えて `reload()` すると、どのタブも描き直されます。タブの側は何も変えていません
- 差し替えるのは `MainFrame` です。`ui/team/TeamSession`（開いている共有プロジェクトの係。画面は持たない）がプロジェクトを開いた・閉じたときに `TeamSession.Listener.projectChanged` を呼ぶので、そこで `TeamSession.storeOf(project)` を渡します。保存先はプロジェクトごとに1つだけ作り、切り替えて戻ってきても同じものを使うので、タスクの番号が変わりません。左上のボタンとメンバー・同期・重なりの表示は `ui/team/ProjectSwitcher`
- 担当者の欄の横のボタンから、メンバーの名前を選べます。`TaskDialog` が `TaskService.assigneeOptions()` を聞き、共有プロジェクトなら `TeamTaskStore` がメンバーと、メンバー以外の担当者（社外の人など）を返します。自分だけのタスクでは空なのでボタンは出ません
- 共有のタスクの ID は UUID ですが、画面は int で扱うので、`TeamTaskStore` が番号を振ります。番号はアプリを閉じるまで変えません。読み直すたびに振り直すと、選んでいたタスクが別のタスクにすり替わるからです
- `TeamTaskStore` は渡したタスクに、そのとき見せた状態の版（`Task.revision`）を付けます。保存のときはその版の状態と比べるので、編集画面を開いたあとに届いた他の人の変更は、黙って上書きせず「重なり」として残ります。変わっていない項目は記録に書きません
- WBS で親を変えると `PARENT` の変更として書きます。階層の深さは記録に書かず、並べるときに親のたどり方から決めます（`TeamReplay`）。自分の下への移動と、3段を超える移動は `TeamTaskRules.requireMovable` が断ります。2人が同時に逆向きに動かして輪になったときは、輪の中で最初に作られたタスクを一番上に出します
- 他の人の変更が届くと、`TeamSession` の自動の読み直しが `Listener.dataChanged` を呼び、`TaskService.reload()` で全タブが描き直されます。ツールバーの「更新」と、ヘッダーの「同期中」を押したときも、共有フォルダを読み直します
- 自動の読み直しと前回のプロジェクトを開くのは `TeamSession.start()` で、`MainFrame.startDueReminders` から呼びます。コンストラクタで始めると、画面のテストが本物の共有フォルダを読みに行くためです。窓を閉じると `MainFrame.dispose` が `TeamSession.stop()` を呼び、読み直しを止めます
- 以前は「チーム」タブにチーム用の一覧と編集画面がありましたが、全タブで共有プロジェクトを扱えるようになったのでなくしました。同じことをする画面が2つあると、どちらを使えばよいか迷うためです

### 「今日」タブと期限の通知は全プロジェクト

WBS などは選んでいる1つのプロジェクトだけを出しますが、「今日」タブと期限の通知は、自分だけのタスクと最近開いた共有プロジェクトをまとめて出します。毎朝どのプロジェクトを開くか考えずに済むようにするためです。

```
TodayPanel / DueReminder → ProjectSources.all() → TaskSource（名前・今選んでいるか・TaskService）の一覧
                                                   ├─ 今選んでいるプロジェクト（MainFrame の TaskService）
                                                   ├─ 自分だけのタスク（共有プロジェクトを選んでいるとき）
                                                   └─ ほかの共有プロジェクト（TeamSession.otherProjects()）
```

- 選んでいないプロジェクトにも、それぞれ専用の `TaskService` を作ります（`ui/main/ProjectSources`）。`MainFrame` の `TaskService` は1つしか保存先を持てないためです。保存先ごとに1つだけ作って使い回します
- `TeamSession` は、最近開いたプロジェクトも裏側で開いて持っておきます（`loadOthers`。持つのは `TeamOtherProjects`）。5 秒ごとの読み直しでそちらも見て、変わっていたら `Listener.otherProjectsChanged` を呼びます。`MainFrame` はそこで `TaskService.reload()` を呼び、「今日」タブを描き直させます
- 番号（ID）はプロジェクトごとに 1 から振るので、別のプロジェクトで同じ番号が出ます。そこで `DueTasks` はプロジェクトごとに作ってから `DueTasks.merge` でつなぎます。全部を混ぜてから作ると、あるプロジェクトの1番を、別のプロジェクトの1番の親と取り違えます（`DueTasksTest.mergeKeepsEachProjectsParentsApart`）
- 「今日」タブでは、行ごとにどのプロジェクトの `TaskService` かを覚えています。Enter と Delete のキーも、`SearchablePanel.selectedTaskService()` で選んだ行のプロジェクトに書きます
- 期限の通知は、`TeamSession.start` が裏側で共有プロジェクトを開き終わってから始めます。先に始めると、最初の通知に共有プロジェクトの分が入らないためです
- 開けなかったプロジェクト（ドライブがまだ準備中など）は、黙って飛ばします
- 「自分の担当だけ」がオンのときは、共有プロジェクトのタスクのうち、担当者がチームの表示名と同じもの（前後の空白と大文字・小文字は無視）と、担当者が空のものだけを出します。空のものも出すのは、誰も担当していない期限に誰も気づかなくならないためです。比べるのは `TaskSource.myName`（`ProjectSources` が表示名を入れる）で、自分だけのタスクは `null` なので全部出ます
- 親かどうかは、絞る前の全件で決めます（`DueTasks.of(tasks, today, include)`）。先に絞ると、ほかの人が担当する子を持つ親が、子のないタスクに見えて出てしまいます
- 表示名を変えると、開いている全部の共有プロジェクトで名前が変わります。前の名前が担当のタスクがあれば「担当者も直しますか？」と聞き、「はい」なら全部を新しい名前に付け替えます（`TeamSession.changeDisplayName` → `TeamProject.reassign`。プロジェクトごとに1回で書きます）。「いいえ」にすると、前の名前のタスクは「自分の担当」から外れます
- 担当者名の比べ方（前後の空白と大文字・小文字を無視）は `model/Assignees.same` の1か所です。「自分の担当だけ」と付け替えの両方が使います
- 他の人が自分を担当にしたり、自分の担当のタスクを変えたりすると、Windows の通知で知らせます。`TeamProject.reload` が、前回までに見ていない・自分の PC 以外の記録を取っておき、`TeamSession.poll` が `takeNotices()` で受け取って `DueReminder.showNotices` に渡します。どれを知らせるかは `TeamNotice.forMe` が決めます（担当者を自分にした記録は「担当にしました」、すでに自分の担当のタスクへの変更は「変えました」。作っただけで担当が自分でないものは知らせません）。コメントの通知は 16 章のコメントの所を見てください
- 知らせないもの: 開いたときにすでにあった記録（アプリを閉じている間の変更）、自分の PC での変更、削除（もう一覧にないため）。2件以上まとめて届いたら、件数とプロジェクト名だけを1回出します

### インポートを速くする

CSV や JSON から共有プロジェクトへ大量に取り込むときは、1件ずつ追加せず `TeamProject.importTasks` でまとめて書きます（記録を作って確かめるのは `TeamImport`）。

- 1件ずつだと、そのたびにファイルを開いて1行足し、ディスクに書き切り（force）、全部の記録を頭から当てはめ直します。件数が増えるほど遅くなり、Google ドライブ上ではとくに遅くなります
- `importTasks` は、先に全部の行をチェックし、1つでもだめなら何も書きません（エラーは「3 件目: 」のように何件目かを付けます）。通ったら `TeamChangeLog.appendAll` で全部の行を1回で書き、当てはめ直しも1回だけです
- 「置き換え」のときは、今あるタスクの削除の記録も同じ1回で書きます
- 親子は、取り込む行の中の何件目が親か（`ImportDraft.parentIndex`）で表します。共有のタスクの ID は書いてみるまで決まらないためです

### 記録の仕組み

```
プロジェクトのフォルダ\        ← このフォルダをメンバーだけに共有する
   ├─ project.json            （プロジェクト名）
   ├─ members\
   │    ├─ tanaka-1a2b3c.json （田中さんの PC の表示名とアプリの版。田中さんの PC しか書かない）
   │    └─ suzuki-4d5e6f.json
   └─ changes\
        ├─ tanaka-1a2b3c.jsonl（田中さんの PC が書いた変更。田中さんの PC しか書かない）
        └─ suzuki-4d5e6f.jsonl
```

- ファイル名の `tanaka-1a2b3c` は端末 ID です。PC ごとに一度だけ作り、Windows の設定に保存します（`TeamSettings`）。同じ人が2台で使っても、別のファイルになります
- 表示名・最近開いたプロジェクト・前回開いていたプロジェクトも `TeamSettings` が覚えます。起動時、前回のプロジェクトを裏側で開きます。ドライブがまだ準備中なら、黙って何もしません
- プロジェクトを作る・参加する・読み直す・重なりを戻すときの読み書きは、`TeamSession` が裏側の1本の列（`TeamBackground`。`team-io` スレッド）に順番に並べます。ネットワークドライブが遅くても画面は止まらず、書き込みの途中に読み直しが割り込むこともありません。作る・表示名の入力の画面は `TeamDialogs`、メンバーの一覧は `TeamMembersDialog`
- 親タスクの進捗と状態は、記録に書かずに表示のたびに子の平均から出します（`TeamReplay.rollUpProgress`）。書くと、子を変えた人全員が親も書き換えることになり、重なりが増えるためです

- 変更は1件ずつ、自分のファイルの最後に1行足すだけです（`TeamChangeLog.append`）。1つのファイルを2台が書かないので、同期で「競合したコピー」ができません
- データベースを共有フォルダに置かないのは、同期の途中のファイルを別の PC が開くと壊れるからです
- 全員のファイルを読み、決まった順に並べて頭から当てはめると、今の一覧になります（`TeamReplay`）。同じファイルからは、どの PC でも同じ結果です
- 並べる順は PC の時計ではなく `clock` という番号です。相手の変更を見たあとの変更は、必ず後ろに並びます
- 2人が互いの変更を知らずに同じ項目を変えたら、後ろに並んだ方を使い、消えた方の値を `TeamConflict` に残します。別の項目なら両方使います
- 「知らずに」は、変更の記録に「この値を見て変えた」という元の記録の ID（`base`）を一緒に書いて判定します。編集画面を開いている間に自動の読み直しが入っても、開いた時点の状態（`TeamState`）を `updateTask(id, 変更, 見ていた状態)` に渡すので、見ていなかった変更は重なりとして残ります
- 画面は 5 秒ごとに `TeamProject.reloadIfChanged` を呼びます。`changes` と `members` のファイルの大きさと更新時刻（`TeamChangeLog.fingerprint`）が前回と同じなら、読まずに終わるので軽い処理です。ただし、相手の PC から Google ドライブ経由で届くまでに 10〜60 秒ほどかかるので、相手の変更が見えるまでの時間はほぼそちらで決まります
- 重なりがあると、ヘッダーにオレンジの「重なった変更 ○件」が出て、押すと見比べる画面が開きます（`TeamConflictDialog`）。1回の保存で複数の項目が重なったら1件にまとめます（`TeamConflictGroup`）。「〇〇さんの値に戻す」は消えた値を普通の変更として書き直し、「タスクを戻す」は削除を取り消す `RESTORE` の記録を書きます（`TeamProject.restoreTask`。消えている親と子もまとめて戻します）
- 「このままでよい」は、その PC だけで覚えます（`TeamSettings.acknowledge`）。記録には書かないので、他の人の画面には残ります。覚える印は `TeamConflict.key()` で、何度読み直しても同じ値になるように作っています
- チームのタスクを削除したあとの「元に戻す」も `restoreTask` です。消した記録は消さずに、戻した記録を足します
- 「プロジェクト ▼」→「変更履歴」で、誰がいつ何を何から何に変えたかを新しい順に見られます（`TeamHistoryDialog`）。中身は `TeamHistory.build` で、記録を一覧と同じ順に当てはめ直しながら、項目ごとの前後の値を拾っています。時刻は書いた人の PC の時計なので、並び順（`clock`）と時刻が前後することがあります
- 共有プロジェクトのタスクを開くと、編集画面の下にコメント欄が出ます（`ui/team/TaskCommentsPanel`。自分だけのタスクには出ません）。「書く」か Enter で、編集画面の「保存」とは別にすぐ書き込みます。コメントは `COMMENT` という記録を足すだけです
- メモは「タスクの説明（今の内容が1つ）」、コメントは「人とのやりとり（書き足していく）」と使い分けます。空のメモ欄とコメントの入力欄には、何を書く所かを薄い文字で出しています（`ui/InputHint`。入力欄の `paintComponent` の最後で呼ぶ）
- 自分のコメントの行には「編集」「削除」が出ます。「編集」は文を入力欄に戻し、「保存」で書き込みます（「やめる」で取りやめ）。「削除」は確かめてから消します。どちらも元の記録は書き換えず、`COMMENT_EDIT` / `COMMENT_DELETE` の記録を足し、`baseEventId` でどのコメントかを指します。一覧では編集したものに「（編集済み）」、削除したものは文の代わりに「（削除されました）」と出て、元の文は変更履歴に残ります（`TeamHistory` がコメントごとに今の文を覚えて、前 → 後を出します）
- 編集・削除ができるのは、この PC で書いたコメントだけです（`TeamProject.canChange`）。表示名は変えられるので、名前ではなく端末 ID（`TeamComment.deviceId`）で決めます。書いた本人しか編集しないので、2人が同じコメントを同時に編集して重なることがありません。`TeamReplay.applyCommentChange` も、書いた PC 以外からの記録や削除したあとの編集は無視するので、どの PC でも同じ結果になります。編集・削除では通知を出しません
- コメントはタスクの値を変えないので、重なりになりません。何人が同時に書いても全部残り、どの PC でも同じ順（`clock` → 端末 ID）に並びます。`TeamReplay.applyComment` はタスクの版（`lastEventId`）を進めないので、コメントを見ずに削除しても「変更と重なった削除」にはなりません。削除したタスクのコメントも残っていて、戻すと一緒に戻ります
- コメントは `TeamState.comments(タスクID)` で取り出します。変更履歴にも「コメント」として出て、自分の担当のタスクに他の人がコメントすると Windows の通知が出ます（`TeamNotice.Kind.COMMENTED`）
- 担当でなくても、この PC からコメントしたことのあるタスクに他の人がコメントすると「あなたもコメントした『…』にコメントしました」と通知が出ます（`TeamNotice.Kind.REPLIED`）。質問への返事に気づけるようにするためです。自分が書いたかは、表示名ではなく端末 ID で決めます。1つのタスクに何件届いても、強い順（担当にした → 担当のタスクにコメント → 自分もコメントしたタスクにコメント → 担当のタスクを変えた）で1件にまとめます
- カンバンのカードと WBS の行には、コメントの件数（「💬 2」）が出ます（`ui/CommentCount`）。`TeamTaskStore.toTask` が、削除していないコメントの文を `Task.comments` に入れます。これは画面に出すためと検索のためだけのもので、保存はしません。コメントは「保存」を通らずすぐ書き込むので、書いたあと `TaskCommentsPanel` が `taskService::reload` を呼んで件数を描き直させます
- 同じ PC で TaskNavi を2つ起動すると、2つが同じ記録ファイルに同時に書きに行き、行が壊れます。`TeamChangeLog.append` は PC 内の一時フォルダのファイルでロックを取ってから書きます。共有ドライブ上のファイルはロックが効くとは限らないためです。`TeamChangeLogConcurrencyTest` が別々の JVM で再現しています

- 同期の途中で切れた行は読み飛ばし、次に読んだときに読めます
- `project.json` と `members\<端末ID>.json` は、追記ではなく丸ごと書き直すファイルです。書いている途中で PC が落ちると、半分だけのファイルが残ります。そこで `TeamFiles.writeAtomically` が、同じフォルダの `.tmp` に書き切ってから名前を付け替えます。付け替えは一瞬なので、元のファイルか新しいファイルのどちらかが丸ごと残ります
- 共有フォルダのファイルは、ほかの PC（や、編集できる人）が置いたものなので信用しません。読むときは `TeamFiles.readText` で大きさに上限を設けます（`changes` の1ファイルは 64 MB、JSON は 1 MB）。超えたファイルは読まずに飛ばし、ヘッダーに「読めないファイルがあります」と名前を出します（`ReadResult.tooLargeFiles`）。巨大なファイルを置かれても、メモリが足りなくなって落ちることはありません

### アプリの版をそろえる

全員が同じ版の TaskNavi を使う前提です。記録の形が違う版が混ざると、人によって見える一覧が変わります。

- 記録の1行ごとに形の番号（`v`）を書きます。`TeamEventCodec.FORMAT` はこのアプリが読める一番新しい番号で、項目や `Op` を足して記録の形を変えたら上げます
- 行に書く番号は `TeamEventCodec.formatOf` が決めます。古い版でも読める記録（追加・変更・削除・戻す）は `1` のまま書き、コメントは `2`、コメントの編集・削除は `3` にします。全部を新しい番号にすると、更新していない人がタスクの変更まで読めなくなるためです。更新していない人には、読めない記録が見えず「アプリの更新が必要」が出るだけです
- 古い版のアプリは、自分より大きい番号の行を読まずに数えます（`TeamChangeLog.ReadResult.newerFormatLines`）。同期の途中で切れた行（`unreadableLines`）とは分けて数えます。切れた行は待てば読めますが、新しい形の行はアプリを新しくするまで読めないためです
- 新しい形の行があると、ヘッダーがオレンジの「アプリの更新が必要」になり、マウスを乗せると行数と今の版が出ます（`ProjectSwitcher.refresh`）
- アプリの版は `pom.xml` の `app.version` です。配布用の JAR の manifest に書き、`AppVersion.current()` が読んでウィンドウのタイトルと起動時のログに出します。IntelliJ から動かしたときは manifest が無いので「開発版」と出ます（`AppVersion.release()` は null）。新しい版を配るときは、`app.version` を上げてから exe を作ります。zip の名前にも版が入ります（`TaskNavi-1.2.0-windows.zip`）
- 記録の形が変わらない更新でも、新しい版に気づけるようにしています。共有フォルダを開くと、`members\<端末ID>.json` に自分のアプリの版（`appVersion`）も書きます（`TeamMembers.register`。版が変わったときだけ書き直す）。ほかのメンバーが自分より新しい版を使っていると、`TeamProject.newerAppMember()` がその人を返し、ヘッダーがオレンジの「新しい版 1.3.0 があります」になります。押すと入れ替え方と、リリースのページを開くボタンが出ます（`TeamUpdateHelp`。「アプリの更新が必要」を押したときも同じ）。配る係は、自分が最初に新しい版で開くだけで全員に知らせが届きます
- 版は `AppVersion.compare` で、点で区切った数を前から比べます（`1.10.0` は `1.9.0` より新しい）。開発版は版を書かず、前に書いた版も消しません。開発版では知らせも出しません。この仕組みより前に作ったアプリは `appVersion` を書かないので、その人の版は分かりません（古い版は知らない項目を読み飛ばすので、困ることはありません）
- メンバーの一覧（「メンバー ○人」）には各自の版が出て、いちばん新しい版より古い人はオレンジになります。誰が入れ替えていないかを配る係が確かめられます
- 入口は `TeamProject`（作る・開く・追加・変更・削除・読み直し）。`project.json` は `TeamProjectFile`、`members` は `TeamMembers`、名前・日付・階層・コメントの確かめと親子のたどり方は `TeamTaskRules`、取り込みの記録づくりは `TeamImport` が受け持ちます。テストは `TeamProjectTest` で、2つのフォルダ間でファイルをコピーして「同期の遅れ」や「オフラインで同時に編集」を再現しています。画面側は `TeamSessionTest`（起動時に開く・閉じる・開き直す・読み直す・ヘッダーの表示）、`TeamPollTest`（5秒ごとの確認）、`TeamBackgroundTest`（裏側の列の順番）が、ダイアログを出さずに確かめます

### 置き場所

- 「共有ドライブ」は、その Google アカウントがどこかの共有ドライブのメンバーでないと `G:\` に現れません。個人の Google アカウントでは作れず、会社のアカウントでも管理者が作成を止めていることがあります
- そのときは `G:\マイドライブ` の中に作り、できたフォルダをブラウザの Google ドライブで、メンバーに「編集者」として共有します。メンバーは共有されたフォルダを「ショートカットを追加」で自分のマイドライブに置くと、`G:\マイドライブ\...` から開けます
- 「新しい共有プロジェクトを作る」の場所の初期値は、共有ドライブ → マイドライブ → ホームフォルダの順に探します（`GoogleDriveFolders`）

### 1台で2人分を試す手順

印刷して使う表は `docs/home-test-checklist.md` です（バックアップから戻す手順も入っています）。

`--team-profile=名前` を付けて起動すると、端末 ID・表示名・最近のプロジェクトを別に持つ「2人目」になります（`TeamSettings.userDefault`）。ウィンドウのタイトルに `[名前]` が付きます。

```
& "（展開した場所）\TaskNavi\TaskNavi.exe" --team-profile=test2
```

1. いつもどおり起動し、左上の「プロジェクト ▼」→「新しい共有プロジェクトを作る」で `G:\マイドライブ` の中に作る
2. もう1つを `--team-profile=test2` で起動し、「プロジェクト ▼」→「共有フォルダから参加する」で同じフォルダを開く。ヘッダーが「メンバー 2人」になることを見る
3. 片方の WBS やカンバンでタスクを追加し、数秒でもう片方のどのタブにも出ることを見る。編集画面の担当者の横のボタンから、2人の名前を選べることも見る
4. 片方で編集画面を開いたまま、もう片方で同じタスクの名前を変える。数秒待ってから開いていた方で別の名前にして保存し、ヘッダーにオレンジの「重なった変更」が出ることを見る。押して「〇〇さんの値に戻す」も試す
5. 片方で削除し、もう片方の「プロジェクト ▼」→「変更履歴」に出ること、「元に戻す」で両方に戻ることを見る
6. ブラウザで Google ドライブを開き、`changes` に2つのファイルが上がっていて、「(1)」の付いたコピーができていないことを見る
7. 共有プロジェクトをもう1つ作り、期限が今日のタスクを入れる。「自分だけのタスク」に戻しても、「今日」タブに両方のプロジェクトのタスクが札付きで出ることを見る
8. 期限が今日のタスクを2つ作り、担当者を自分と相手に分ける。「今日」タブで、「自分の担当だけ」がオンなら自分の分だけ、オフにすると両方出ることを見る
9. 相手の側でタスクを作り、担当者を自分の表示名にする。数秒で自分の側に「〇〇さんが「…」をあなたの担当にしました」と Windows の通知が出ることを見る
10. 相手の側でそのタスクを開き、コメントを書く。自分の側に「コメントしました」の通知が出て、タスクを開くとコメント欄に出ることを見る。カードと WBS の行に「💬 1」が出ることも見る。相手のコメントには「編集」「削除」が出ず、相手の側で編集すると自分の側に「（編集済み）」が出ることも見る

この手順で、Google ドライブ上でのファイルの読み書き・自動の読み直し・重なりの検出は確かめられます。別の PC から同期されてくるまでの時間だけは確かめられません。Google Drive for desktop の「アカウントを追加」で2つ目の Google アカウントをつなぐと、別のドライブ文字（H: など）に出るので、そちらから同じフォルダを開けばクラウド経由の同期も1台で試せます。
